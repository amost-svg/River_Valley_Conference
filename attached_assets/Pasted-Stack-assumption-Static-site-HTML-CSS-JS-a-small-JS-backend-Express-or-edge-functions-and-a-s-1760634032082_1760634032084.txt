A2. Calendar Data: Fix Dates + Make It Fast

Symptoms: Volleyball conf. games display Mon/Wed but should be Tue/Thu.
Root causes to check and fix:

Spreadsheet import parses dates as strings; ensure timezone is America/Chicago.

Avoid JS Date constructor on ambiguous “MM/DD/YYYY” strings. Use Luxon or Day.js with timezone:

Parse with known format (e.g., MM/dd/yyyy) and explicit zone.

Convert to local zone before rendering.

Verify no off-by-one error from UTC midnight conversion.

Performance (static load):

On build (or by an admin “Sync Games from Sheet” button), generate public/data/games.json (already parsed and normalized).

Calendar bootstraps from games.json immediately (no remote fetch or sheet roundtrip).

Add simple ETag caching headers and version the JSON (e.g., games.v{timestamp}.json) so the client always gets the latest after a sync.

Keep a lightweight admin route (/admin/sync) to re-pull from the spreadsheet on-demand; show last sync timestamp.

Acceptance checks:

Pick dates from the sheet known to be Tue/Thu and verify calendar shows Tue/Thu.

Page first paint shows calendar with events in < 300ms after DOM ready (from local JSON).

If no internet after initial load, calendar still renders from cached JSON.

G) Technical Implementation Notes
G1. Date/Time correctness

Use Luxon (or Day.js + timezone) everywhere.

Always parse sheet values with explicit format and zone: 'America/Chicago'.

Store canonical date/time in UTC in the DB (ISO 8601), plus is_conference boolean.

On render, convert to local zone.

G2. Fast Calendar Load

Build step (or admin “Sync”) writes a flat JSON (public/data/games.json) with only what the UI needs:

[
  {
    "id": 123,
    "sport": "Volleyball",
    "level": "Varsity",
    "conference": true,
    "startISO": "2025-09-04T18:30:00-05:00",
    "home": "Beecher",
    "away": "Grant Park",
    "location": "Beecher HS",
    "status": "scheduled"
  }
]


Calendar reads this immediately; no multi-hop fetch.

G3. Minimal backend

If using Express:

Routes: /api/games, /api/results, /api/pending/games, /api/pending/results, /api/standings/recalc, /api/news, /admin/sync.

Auth middleware (JWT or Supabase Auth).

If using Supabase only (no server):

Tables as described; use Row Level Security (RLS) to separate roles.

Use Supabase Functions (Edge) for “recalc standings” and “sync” if needed.

Storage buckets for news PDFs and images.

G4. Standings recalculation

Query approved results joined to games:

For each sport + school:

Overall: count wins/losses across all final games.

Conference: same with is_conference=true.

Non-conference: overall minus conference.

Compute Win%, Streak, Last 5.

Cache results in a materialized table for instant load; refresh on demand.

G5. Volleyball scoring model

results.sets_json example:

{
  "bestOf": 3,
  "sets": [
    {"home": 25, "away": 18},
    {"home": 19, "away": 25},
    {"home": 15, "away": 9}
  ]
}


Winner = first to 2 sets; allow “won in two” or “won in three” display.

G6. UI Components (suggestions)

Use a lightweight calendar (FullCalendar) bound to the prebuilt JSON.

Tables: use a sortable table component; keyboard accessible; aria labels.

Modals for Add Game, Report Score, Review Pending; show success toasts.

G7. Security & Roles

Gate admin endpoints by role; never trust client role claims.

Log all approvals/rejections with admin id + timestamp.

G8. Testing/Checks

Unit tests for date parsing (Mon/Wed bug prevention).

E2E happy path: add game → approve → report score → approve → recalc standings → dashboard mini reflects change.

News upload CRUD works with real file(s).
